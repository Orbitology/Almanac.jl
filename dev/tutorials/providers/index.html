Bodies and frames from your own functions

A trajectory that the program computes (with a propagator, an optimizer, an interpolation) can be used directly, without writing an SPK. add_ephemeris! makes a function the source of the state of a body, and add_frame! of the orientation of a frame. Every call that takes a body or a frame then uses them: with any aberration correction, in surface geometry, in event searches and in tables.

Define a body

The function takes an epoch (ET) and returns the position (km) and the velocity (km/s) relative to the center, in the given frame. Here, a circular orbit of radius 8000 km around the Earth:

using Almanac

μ = 3.986004418e5                           # km³/s², the Earth
r = 8000.0                                  # km
n = sqrt(μ / r^3)                           # rad/s
circular(et) = [r * cos(n * et), r * sin(n * et), 0.0,
                -r * n * sin(n * et), r * n * cos(n * et), 0.0]

t0 = str2et("2025 MAR 01 00:00:00 UTC")
add_ephemeris!(circular, -1000, "EARTH", "J2000", t0, t0 + 86400.0; name = "my orbit")
state, light_time = spkezr(-1000, t0 + 600.0, "J2000", "LT+S", "PROBE")
round.(state; digits = 3)
6-element StaticArraysCore.SVector{6, Float64} with indices SOneTo(6):
  25420.091
  -6824.187
 -15933.754
     -6.555
     -0.928
      1.007

The body acts as if it were a file loaded at the time of the call. It takes priority over the files loaded earlier, which still apply outside its interval, and unload with its name removes it.

kinfo("my orbit")                           # (type, meta-kernel, handle)
("SPK", "", 0)

Define a frame

The function returns the rotation from the new frame to its relative frame, the matrix of pxform(new, relative, et). The other arguments are the name and the ID code of the new frame, its center and its relative frame:

spin(et) = (c = cos(n * et); s = sin(n * et); [c -s 0; s c 0; 0 0 1])
add_frame!(spin, "ORBIT_FIXED", 1_400_000, "EARTH", "J2000")

spkpos(-1000, t0 + 600.0, "ORBIT_FIXED", "NONE", "EARTH")[1]
3-element StaticArraysCore.SVector{3, Float64} with indices SOneTo(3):
 8000.0
    0.0
    0.0

In that frame the spacecraft stays on the X axis.

Load states as a kernel, with no file

add_ephemeris! calls the function at every query. When the function is expensive (a numerical propagator), or when the states already exist as samples, load them as a kernel instead. The kernel lives in memory: no file is written, and queries cost what they cost on an SPK file.

load_samples! loads states at epochs, which queries interpolate with SPK type 13 (Hermite, which uses the velocities) or type 9 (Lagrange):

ets = collect(t0:60.0:(t0 + 3600.0))
load_samples!("samples", -1001, "EARTH", "J2000", ets, circular.(ets))
vnorm(spkpos(-1001, t0 + 1234.5, "J2000", "NONE", "EARTH")[1] - circular(t0 + 1234.5)[1:3])  # km
1.7989122931461998e-7

load_function! fits any function with Chebyshev polynomials to a tolerance and returns the measured errors in position (km) and velocity (km/s). The function is called only during the fit:

poserr, velerr = load_function!("fit", circular, -1002, "EARTH", "J2000", t0, t0 + 86400.0; tol = 1e-6)
(9.255898395112847e-7, 8.166799922824315e-10)

An ODESolution of DifferentialEquations.jl is such a function, through a closure such as et -> sol(et - et0)[1:6]. Check three things in it: the time of the solver is usually counted from a start epoch et0, not from J2000; the state may hold more than six components (a mass, a transition matrix); and the units must be km and km/s.

For several arcs (a trajectory with burns) or another SPK type, write the segments yourself into an SPK in memory, from spkops, with any writer, and load it with furnsh. A kernel can bring names of bodies, which go away with it; save_kernel writes the same bytes to a file:

h = spkops()
half = length(ets) ÷ 2
spkw13(h, -1003, 399, "J2000", ets[1], ets[half], "arc 1", 7, circular.(ets[1:half]), ets[1:half])
spkw13(h, -1003, 399, "J2000", ets[half], ets[end], "arc 2", 7, circular.(ets[half:end]), ets[half:end])
furnsh(h; name = "arcs", bodies = ["MY PROBE" => -1003])
save_kernel(h, joinpath(mktempdir(), "arcs.bsp"))
spkcls(h)
bodn2c("MY PROBE")
-1003

The load takes a copy, so close the handle after furnsh or save_kernel, not before.

Epoch types and thread safety

This section is about the functions of add_ephemeris! and add_frame!; the function of load_function! gets Float64 epochs, during the call only. The epoch passed to the function is not always a Float64. It is a ForwardDiff.Dual when the caller differentiates, and an internal Taylor number when a call needs derivatives of order 2 or more (an LT+S state of an observer, sxform of a frame). Plain arithmetic and the functions of Base (sin, cos, sqrt, ...) work with all of them. A function that branches on the epoch, or calls code that accepts only Float64, works only in the calls that need no derivative of order 2, such as geometric states and pxform, and only with a Float64 epoch.

The function is called from every thread that queries, so it must not change shared data. Beware of closures that assign to a variable of the enclosing function, because they share it. Declare such variables local in the closure, or give them names that the enclosing function does not use.
